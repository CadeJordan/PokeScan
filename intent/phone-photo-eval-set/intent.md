# Phone-photo evaluation set

## Intent

Measure how the served pipeline grades phone photos of real slabbed cards, which are what users upload, instead of PSA's catalogue shots. Build a small labelled set from the owner's own slabs, run it once through `ml.eval.evaluate --manifest`, and report the accuracy and where it breaks, by shooting condition. This is [[cv-ml-improvement-plan]] item 13 (open question 8). It changes no model and no detector; it produces numbers and a ranked list of failures for the next specs.

## Why

- Every number so far (test MAE 0.443, exact 65.3%, the CV gates) is on PSA catalogue photos: one studio setup, slab square to the camera, even light, 1024 px.
- Several shipped changes were checked here only against simulated phone conditions (`ml.eval` perturbations: rotations, JPEG, swaps):
  - upload normalisation (EXIF, size cap, sideways retry) [[serve-input-normalization]];
  - rejecting unusable uploads [[reject-unusable-uploads]];
  - the side/orientation guard [[face-side-orientation-guard]];
  - the slab detector [[tighter-slab-crops]].
- `ml.eval.evaluate --manifest` already exists (`ml/eval/evaluate.py:351`, README "Raw (unslabbed) cards") and has never had data.

## The set

**What:** the owner's own PSA-slabbed cards. The grade is the one on the PSA label; the cert number is on the label too.

**How many:** the target is 50–100 cards. With n = 50, MAE's 95% CI is roughly ±0.15; with 100, ±0.10. Fewer than ~30 cards reads only as a smoke test, and the report says so.

**Shots per card (protocol, to confirm in Q2):** two pairs (front + back) per card:
1. **Careful:** slab flat on a plain, dark, non-reflective surface, phone square above it, indirect daylight or room light, no glare across the card, slab filling most of the frame.
2. **Casual:** how a user would actually do it: in hand or on a table, some tilt (up to ~20°), normal indoor light, whatever background.

The two pairs per card let the report separate "phone vs catalogue" from "careful vs casual" on the same cards. Shots are taken with the phone camera app at default settings and copied off the phone unedited (EXIF kept, no crop, no screenshot), so the upload path sees what a user's browser would send.

- **Format:** JPEG. The API accepts JPEG/PNG/WebP only (`preprocess.UPLOAD_FORMATS`). An iPhone shooting HEIC needs Settings → Camera → Formats → "Most Compatible" first, or the files get converted to JPEG on transfer. A HEIC file in the set is a manifest error, not a silent skip.

## Layout

```
data/phone_eval/                  (gitignored; owner's photos, never committed)
  photos/<cert>_<shot>_<face>.jpg  e.g. 82001234_careful_front.jpg
  cards.csv                        owner-written: cert, grade, [notes]
  manifest.csv                     generated by the helper
```

- `cards.csv` is the only file the owner writes by hand: one row per card with the cert and the grade on the label.
- The helper (below) pairs the photos by file name, checks them, and writes `manifest.csv` with columns `front,back,grade,id,shot,cert,in_db_split`.

## Code changes (small)

1. **`.gitignore`:** add `data/phone_eval/`. Today only named subfolders of `data/` are ignored, so the owner's photos would otherwise show as untracked.
2. **`ml/eval/phone_set.py` (new):** `python -m ml.eval.phone_set build data/phone_eval` reads `cards.csv` and `photos/`, and writes `manifest.csv`. It fails loudly, listing every problem at once, on:
   - a photo name that doesn't parse, or a cert not in `cards.csv`;
   - a card with a front but no back for a shot (or the reverse);
   - a grade outside 1..10, a duplicate cert;
   - a file PIL can't open as JPEG/PNG/WebP (e.g. HEIC).

   It looks each cert up in the DB **read-only** and records `in_db_split` (train / val / test / absent); see "Leakage" below. It writes only `manifest.csv`, inside the folder it was given.
3. **`ml/eval/evaluate.py`:** `load_manifest` keeps optional extra columns as per-sample tags. `build_report` adds `by_tag`, the same count / MAE / exact / n_would_reject breakdown as `crop_kinds`, for each tag column (`shot`, `in_db_split`). No change for DB splits, whose reports stay byte-identical apart from an absent `by_tag`.
4. **Cluster-aware CIs:** with two shots per card, the rows aren't independent. For manifest runs that have a `cert` column, `overall_ci` resamples cards, not rows.
5. **Tests** (`tmp_path` only, synthetic images): the helper's pairing and every error case; `load_manifest` tags; `by_tag`; the card-level bootstrap; the existing manifest test unchanged.

## Leakage

If the owner's certs were harvested into the DB, the model may have trained on PSA's catalogue photo of that very card. Then a phone score on that card is optimistic. The report splits results by `in_db_split`:
- **absent** or **test**: the clean number, the one to quote;
- **train / val**: reported separately and flagged, not mixed into the headline.

If `in_db_split` is "test", the cert's catalogue photo is also already in the test-split predictions, so there is a free **paired comparison**: the same card, catalogue photo vs phone photo.

## Run and report

1. The owner drops photos and `cards.csv` into `data/phone_eval/`.
2. `python -m ml.eval.phone_set build data/phone_eval`.
3. One run: `python -m ml.eval.evaluate --manifest data/phone_eval/manifest.csv --out-dir test-artifacts/eval/phone_set`. CPU is fine at this size.
4. Write up in this spec's Results section:
   - overall MAE / exact / QWK with card-level CIs, next to the catalogue test numbers (0.443 / 65.3% / 0.512);
   - by shot (careful vs casual), by `in_db_split`, by crop kind;
   - `n_would_reject` (how many pairs a user would get a 422 for) and what the notes said (upside down, swapped);
   - paired catalogue-vs-phone on any test-split certs;
   - overlays of every rejected pair and every miss by ≥ 2 grades to `test-artifacts/overlays/phone_set/`;
   - a ranked list of failure causes, each with a count, as candidate next specs.

This set is an **evaluation set only**: nothing is tuned or selected on it, and it's never added to training. The same rule as the test split.

## Out of scope

- Raw (unslabbed) cards: there's no label until they're graded. A later set.
- Training on phone photos, or any model, threshold or detector change. Those are follow-up specs driven by the failure list.
- A frontend change.
- Photos of other people's cards, or scraped listing photos.

### Implementation (2026-11-01)

- `.gitignore`: `data/phone_eval/`.
- `ml/eval/phone_set.py`: `build_manifest(folder, db_path)` / `write_manifest` (plain functions) behind `python -m ml.eval.phone_set build <folder> [--db-path]`. Names parse case-insensitively (`.jpg/.jpeg/.png/.webp`); each photo is checked with the served decode (`preprocess.decode_image`, so only `UPLOAD_FORMATS` open). All problems are collected and raised as one `PhoneSetError`, each line naming the file (or `cards.csv:<line>`); then nothing is written. Also reported: a non-numeric cert, a half or non-numeric grade (PSA 8.5 etc. isn't a model grade), a second photo for the same cert/shot/face, a missing `cards.csv`/`photos/`, and a parseable name with another extension (e.g. `.heic`). `Thumbs.db`, `desktop.ini` and dotfiles are skipped. Warnings, not failures: a card in `cards.csv` with no photos, a card with only one of the two pairs, a missing or unreadable DB, which makes every cert `unknown` (never `absent`, the clean label). After the test agent: the DB path is URI-escaped (`#`, `%` in a path opened the wrong file), a non-UTF-8 `cards.csv` is a problem ("save as CSV UTF-8"), and certs must be ASCII digits.
- `in_db_split` comes from a plain `sqlite3` connection opened with `mode=ro`, not `ml.data.db.connect`, which creates the schema and migrates columns (a write). A cert in the DB with a NULL split is `unassigned`; any other split value (e.g. `excluded`) is kept as is.
- `ml/eval/evaluate.py`: extra manifest columns become `Sample.tags` and `tag:<column>` rows; `pipeline.by_tag` gives n / MAE / exact / `n_would_reject` per value of each tag column except `cert`, which instead groups the bootstrap: `overall_ci` and the per-grade MAE CIs resample cards (`overall_ci.n_groups` says how many). Without tags (every DB split) the report is unchanged: no `by_tag`, the same row bootstrap and draws. The CLI prints a `by <tag>:` line per tag and notes card-level CIs.
- Tests: `ml/tests/test_phone_set.py` (helper, tmp folders + tmp SQLite DB), and tags / `by_tag` / grouped bootstrap / unchanged DB-split report in `ml/tests/test_eval_metrics.py`.

## Owner questions

1. **Which cards?** *Recommendation:* every slab you have, up to 100, whatever the grades. A spread below 9 helps most, since the catalogue set is mostly 9s and 10s, but don't skip any to get it.
2. **Shot protocol:** two pairs per card (careful + casual) as above, or one pair (casual only)? *Recommendation:* two pairs. It doubles the shooting (~2 min per card), but it's the only way to tell "phone photos are worse" from "careless phone photos are worse".
3. **Phone:** iPhone or Android? With an iPhone, switch to "Most Compatible" (JPEG) first. Also: is it OK to record the phone model from EXIF in the report? *Recommendation:* yes; it stays in the gitignored folder and the local report.
4. **Location and writes:** photos in `data/phone_eval/` (you copy them in), and the helper may write `data/phone_eval/manifest.csv` there. Nothing else under `data/` is written. OK? *Recommendation:* yes.
5. **Where to record the result:** in this spec only (like tighter-slab-crops), or also an ADR since it's the first real-world number? *Recommendation:* the spec now; an ADR only if the result changes what the app promises (e.g. a "photograph it like this" guide in the UI).

## Owner decisions (2026-11-01)

1. **All slabs, up to 100**, whatever the grade.
2. **Two pairs per card:** careful + casual, as in the protocol.
3. Phone model from EXIF may be recorded in the local report (default; not asked separately). Use JPEG ("Most Compatible" on an iPhone).
4. **Approved writes:** the owner copies photos into `data/phone_eval/`; the helper writes only `data/phone_eval/manifest.csv`. The DB is read-only. Nothing else under `data/` is written.
5. **Record the result in this spec only.** An ADR only if it changes what the app promises.

## Facts vs assumptions

- **Fact:** the manifest loader, the eval report, the reject counts and the notes already exist and run on the served path.
- **Fact:** `data/phone_eval/` isn't gitignored today.
- **Assumption:** PSA's label grade is the ground truth here, as it is for the catalogue set.
- **Assumption:** most of the owner's slabs are 9s and 10s, like the catalogue set. If so, the result says little about low grades; the report will show the grade spread.
- **Unknown:** whether the owner's certs are in the DB. The helper finds out read-only.
